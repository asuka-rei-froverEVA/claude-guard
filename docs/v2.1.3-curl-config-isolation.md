# v2.1.3 curl 配置来源与信任锚隔离

## 问题

Guard 的每一道网络门禁——出口 IP 探测、IPv6 泄漏检查、TLS/MITM 预检、watchdog API
探针——都靠 `curl` 执行。而 **curl 默认会读取 `~/.curlrc`**。

`official_net_env` 和 `clean_env` 都用 `env -i` 清空父环境，看起来隔离得很干净，但两者
都把 `HOME` 传了进去：

```bash
official_net_env() {
  env -i \
    HOME="$HOME" \
    ...
}
```

于是 `~/.curlrc` 一直对门禁生效。实测（macOS，curl 8.7.1）：

```
# ~/.curlrc 放一个金丝雀
不带 -q → > User-Agent: CURLRC-CANARY
带 -q   → > User-Agent: curl/8.7.1
```

### 实际影响

`.curlrc` 里一行 `insecure` 就足够：

```
# ~/.curlrc 含 insecure，打 self-signed.badssl.com
不带 -q → exit=0
带 -q   → exit=60
```

配合一个中间人，攻击链是完整的：

1. 证书校验被 `.curlrc` 关闭，MITM 的证书链被接受。
2. 中间人伪造 `api.anthropic.com/cdn-cgi/trace` 的响应，塞一个白名单内的 `ip=`。
3. `get_current_ip_once` 采信它，出口门禁通过。
4. TLS 预检那步只要 MITM 的 issuer 不撞上关键词黑名单（真实的拦截设备不会自报家门），
   一并通过。

**结果是整套启动门禁在一个用户自己都可能忘了的配置文件面前完全失效。**

需要说明的是，在 OpenSSL 系后端上 `check_tls_host` 有一层歪打正着的保护：`insecure`
模式下 curl 打的是 `SSL certificate verify result: ... continuing anyway.`，而不是
`SSL certificate verify ok`，所以 TLS 那步仍会失败。但 `get_current_ip_once` 和 IPv6
检查只有 `curl -fsS`，没有任何证书字符串校验——**出口门禁这条路是真的裸奔。**

## 决策

### `-q` 必须是第一个参数

curl 的 `-q` / `--disable` 用于禁用配置文件，但它**只有作为 curl 后面的第一个参数时才
生效**，位置靠后无效。因此所有调用统一写成：

```bash
official_net_env curl -q -4 -x "$CLAUDE_PROXY_URL" --cacert "$CA_CERT_FILE" ...
```

覆盖四条 HTTPS 路径：

| 路径 | 函数 |
| --- | --- |
| 出口 IP 探测 | `get_current_ip_once` |
| IPv6 泄漏检查 | 启动门禁内联 |
| Anthropic API TLS 预检 | `check_tls_host` |
| watchdog API 探针 | `check_api_path_once` |

`bin/claude-cc` 的本机 endpoint 探针也加了 `-q`。它打的是 loopback HTTP，不涉及 CA，
因此不加 `--cacert`；但 `.curlrc` 里的 `proxy` 一样能把这条探针引到别处，所以 `-q` 有
必要。

### 显式 `--cacert`，不只依赖 `SSL_CERT_FILE`

`official_net_env` 一直在设 `SSL_CERT_FILE="$CA_CERT_FILE"`。这在 OpenSSL 系后端上有效，
但 **Schannel 会直接忽略它**，改用 Windows 原生证书库——也就是说"固定 CA bundle"这个
意图在那些平台上从未真正生效过。

显式传 `--cacert "$CA_CERT_FILE"` 让信任锚变成命令行上的确定事实，而不是一个可能被后端
无视的环境变量。环境变量保留，两者并存。

### 不放宽任何既有检查

本版只做减法：把 curl 可能从外部吸收配置的通道关掉，把信任锚钉死。没有任何一条既有检查
被放宽或跳过。

## 测试

`tests/curl_hardening.sh`：

1. **首参断言。** 记录型假 curl 把每次调用的完整 argv 写进日志，测试尾部逐行断言
   `$1 == "-q"`。断言的是**运行时真实 argv**，不是对源码 grep——后者挡不住新增的调用点。
2. **`--cacert` 断言。** 四条 HTTPS 路径分别按 URL 特征定位，断言 argv 里含精确的
   `--cacert <配置里的路径>`。
3. **`.curlrc insecure` 回归。** 假 curl 忠实模拟 curl 自身的行为：只有当 `-q` 不是首参
   时才读 `~/.curlrc`；读到 `insecure` 就当校验已关闭，放行一条被伪造的响应——`ip=` 用
   的正是白名单里那个 IP，issuer 故意不撞关键词黑名单。断言启动门禁必须 `exit 3`。

`tests/watchdog_runtime.sh` 同步加了 argv 断言，覆盖 `check_api_path_once`——它不在
`--precheck-only` 的路径上，只能由 watchdog 集成测试触达。

### 断言必须踩到参数边界

第一版的 argv 记录用的是 `args="$*"`，断言用 `case`/`grep` 在拼好的一整行里找
`--cacert <path>`。这有两个问题：

1. **参数边界丢失**：CA 路径里只要有空格，拼行后就分不清是一个参数还是两个。
2. **只证明了 `--cacert` 出现过**：把实际路径改成 `/definitely/wrong-ca.pem`，
   `tests/watchdog_runtime.sh` 依然全绿。

改法：fixture 按参数逐个 TAB 分隔写入，断言改为 awk 按 `\t` 切分、找到 `--cacert` 后
要求**紧跟的下一个字段严格等于** `$CA_CERT_FILE`。`tests/curl_hardening.sh` 的 CA 路径
现在故意带一个空格（`$TMP_DIR/ca dir/cert.pem`），把这条边界锁死。

### CC 通道：`-q` 挡不住环境代理

`bin/claude-cc` 的 `check_endpoint_protocol` 是全项目唯一跑在**调用者原始环境**里的
curl——`claude-guard` 的每条 curl 都经过 `clean_env` / `official_net_env` 的 `env -i`，
而 `claude-cc` 没有这一层。所以：

- `-q` 挡掉了 `~/.curlrc`；
- 环境里的 `http_proxy` / `HTTP_PROXY` / `ALL_PROXY` **照样生效**。

`EXPECTED_BASE_URL` 早在 `bin/claude-cc:372` 就被校验为 loopback。一条本该直连本机的
探针被引到代理上，「端点可达 + 协议正确」这个结论就由代理说了算。

curl 对 loopback 是否默认绕过代理**随版本和构建而异**：本机 curl 8.7.1
(macOS/SecureTransport) 实测不会走代理，但 shipped man page 里没有任何一句记载这个默认，
curl 上游对此仍是 open discussion（curl/curl#16119）。这不是可以依赖的行为，尤其是
Linux 侧。改为显式 `--noproxy '*'`——它同时覆盖环境变量和 `.curlrc` 里的 `proxy`。

`tests/cc_lane.sh` 的假 curl 现在忠实模拟这两个配置来源，并在判定「会被引走」时记一笔
`curl.diverted`；测试跑一次敌意环境（`~/.curlrc` 里 `proxy =` + 环境里三个代理变量），
断言这个文件必须为空。

## 反向验证

回退对应改动后用例确实失败：

```
去掉出口探测的 -q          → every curl invocation must pass -q as the first argument
去掉全部 -q                → a ~/.curlrc containing "insecure" must not let the gate pass
check_tls_host 的 --cacert 改错 → Anthropic API TLS / Claude 登录 TLS must pass --cacert "..."
IPv6 检查的 --cacert 改错  → IPv6 泄漏检查 must pass --cacert "..."
出口探测的 --cacert 改错   → 出口 IP 探测 must pass --cacert "..."
watchdog 的 --cacert 改错  → watchdog API probe must pass --cacert "..."
claude-cc 去掉 --noproxy   → loopback probe was diverted to a proxy
claude-cc 去掉 -q          → every cc-lane curl invocation must pass -q as the first argument
```

四条 HTTPS 路径的 `--cacert` 值分别验证：其中三条由 `tests/curl_hardening.sh` 覆盖，
`check_api_path_once` 不在 `--precheck-only` 路径上，由 `tests/watchdog_runtime.sh` 覆盖。

其中最决定性的是第二条：摘掉全部 `-q` 后，`.curlrc` 里一行 `insecure` 让门禁**完整放行**
（`exit 0`），伪造的白名单 IP 和 MITM issuer 双双过关。

## 附带更正

README「平台支持」里原先写着「确认 PATH 里 Git for Windows 的 `mingw64\bin\curl.exe`
排在 `C:\Windows\System32\curl.exe` 前面」。社区反馈该二进制在部分版本上**同样是
Schannel 后端**，因此仅调整 PATH 顺序并不保证换到 OpenSSL。

已改为：一律以 `curl -V` 的实际输出为准，不要按二进制的来源推断。

## 边界

不改变网络目标、探测频率、失败阈值、`allowed_ips` 语义、OAuth profile、session、客户端
版本与哈希、生命周期策略，也不改变 CC Switch 通道的任何一项校验。

一处确实改变的网络行为：CC 通道的本机 endpoint 探针从此一律直连 loopback，不再受环境
代理或 `~/.curlrc` 里的 `proxy` 影响。这是修复而不是回归——那条 URL 早就被校验为
loopback，走代理从来就不是预期路径。

如果你的 `~/.curlrc` 里有 `insecure`、`-k`、`proxy` 或自定义 CA 设置，升级后它们不再影响
Guard 的探测——这正是本版的目的。
