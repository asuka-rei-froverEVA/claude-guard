# v2.1.2 出口探测与 API 同策略

## 问题

启动门禁的 `allowed_ips` 白名单要回答一个问题：**Claude 的流量现在从哪个 IP 出去。**

`get_current_ip_once` 此前默认探测 `ipinfo.io` 和 `api.ipify.org`。Clash、Mihomo、
Surge 这类代理按**目标域名**选择出站策略，而这两个域名通常不在用户的 Anthropic 分流
规则里，会落到兜底策略。于是探测量到的是另一条线路的出口。

两个失效方向都成立：

- 启动期误拒——探测链路的出口不在白名单，`exit 3` / `exit 4`，但 Claude 实际链路完全正常。
- 漏过真实漂移——Claude 的出口变了，探测链路没变，watchdog 毫无反应。**而后者正是这
  个检查存在的理由。**

本项目默认代理端口是 `7897`（与 Clash Verge Rev 的默认 mixed port 一致；Mihomo 自身
文档给的示例通常是 `7890` / `7892`），核心用户群大概率受影响。

外部贡献者 erwanjun 在 #4 中定位并修复了这个问题。

## 决策

### 默认探测 Anthropic 自有域名

默认值改为 `https://api.anthropic.com/cdn-cgi/trace`。这个域名必然命中用户已有的
Anthropic 分流规则，探测流量与 API 流量走同一条策略。

措辞上要精确：命中同一条**策略**是成立的；但策略组是 url-test 或负载均衡时，同一条
策略的两次请求仍可能出不同 IP。固定／黏性出口下才等价于同一出口。

`get_current_ip_once` 同时接受裸 IP 响应体和 trace 的 `key=value` 格式，
`CLAUDE_GUARD_IP_CHECK_URLS` 覆盖行为不变，向后兼容。

### 否掉跨域 fallback

原始 PR 保留了 `claude.ai/cdn-cgi/trace` 作为兜底。**这条 PR 自己的论据就否掉了它**：
既然探测必须与 API 流量命中同一条分流策略，那么 `claude.ai` 作为另一个 hostname 就不
满足这个前提——认证域名和 API 域名在规则里分开配是常见做法。

主端点探不到时换个域名再问一次，等于退回到本次要解决的那个问题：拿一条不确定链路的
出口去判定白名单。正确行为是 fail-closed。

### 知情接受的代价

默认单一源 + 启动期 fail-closed，意味着该端点不可用时用户被硬挡在门外
（`IP_CHECK_RETRIES=3` 只能缓解）。这是自觉的取舍：一个会在错误链路上给出「通过」的
门禁，比一个偶尔挡住人的门禁危险得多。

想保留兜底的用户可以自己写进 `CLAUDE_GUARD_IP_CHECK_URLS`，这条路径保住了。

### 保留 curl 的退出状态

旧代码用 `curl ... || true` 抹掉退出码。curl 因 `--max-time` 超时（退出码 28）但已吐
出包含 `ip=` 的部分响应体时，会被当成功结果接受。

这个写法是历史遗留，不是本次引入；但旧默认值下截断的裸 IP 大概率过不了 `is_ipv4`，而
trace 的部分响应可能已经包含完整的 `ip=` 字段——同一个写法在新默认值下暴露面明显变大，
因此一并收掉：先判定 curl 成功，再解析响应体。

## Schannel：明确拒绝，不静默降级

Windows 原生 curl（Schannel 后端）跑不了 `check_tls_host`，但报错是「未显示证书验证
通过」，读起来像在指控用户被中间人劫持。见 #6。

问题不在 `grep 'SSL certificate verify ok'` 这一行。紧接着还要从 curl 的 verbose 输出
里 `sed` 出证书 `issuer:`，拿它匹配 Charles / Fiddler / Zscaler 这类 MITM 特征——**TLS
预检存在的理由就是这个检查**。Schannel 两样都不打印。

因此放宽字符串匹配并不能恢复检查，只会把这一步变成什么都不查的空步骤。这里选择明确
报错：

- 后端识别先于 curl 退出码判定。Schannel 在证书校验失败时同样以非零码退出，若先判退
  出码就会报「无法连接或验证证书」，把平台限制说成网络或代理问题。
- 命中后立即 `break`：平台不支持是确定性结果，重试三次纯属浪费。
- 只探测了一次，收尾文案就不能声称「经过 3 次尝试」——不支持的后端走独立文案。

`check_api_path_once`（watchdog 的 API 探针）依赖同样的 OpenSSL verbose 输出，在
Schannel 上同样不可用。由于启动门禁已经先行拒绝，watchdog 不会走到这一步。

README 新增「平台支持」一节，说明 macOS 已验证、Linux 需自行设置
`CLAUDE_GUARD_CA_CERT`（默认值 `/etc/ssl/cert.pem` 是 macOS 路径）、Windows 原生不支持
及两条绕行方案。

## 边界

本版**改变了出口 IP 探测的网络行为**。探测频率、失败阈值、`allowed_ips` 语义、
OAuth profile、session、客户端版本与哈希、生命周期策略和 CC Switch 通道行为均不变。

已显式设置 `CLAUDE_GUARD_IP_CHECK_URLS` 或 `CLAUDE_OFFICIAL_IP_CHECK_URLS` 的用户不受
影响。原先依赖默认值、且代理规则里没有把 `api.anthropic.com` 指向固定出口的部署，升级
后可能在启动期以 `exit 3` 被拒——这是设计意图，此前量到的出口本就与 Claude 实际链路
无关，通过检查只是假象。

## 验证

`tests/ip_probe_format.sh`：

- trace 与裸 IP 两种响应体格式都能解析。
- trace 解析结果不在白名单时仍然 fail-closed。
- **默认配置**下主端点失败必须 `exit 3`，并断言全程没有请求过 `claude.ai`。
- curl 吐出含完整 `ip=` 的部分响应后以 28 退出时必须 `exit 3`。该用例的白名单里正好
  有部分响应中的那个 IP：一旦采信就会 `exit 0` 放行，因此断言是紧的。

`tests/tls_backend_platform.sh`：

- Schannel 在 curl 退出码 `0` 和 `60` 两种形态下都必须 `exit 7`、报错指名后端、不回落
  到含糊文案、不重试、不声称重试过。
- fixture 复用 `config/official-settings-lifecycle.example.json`，生命周期策略升级时
  不会过期。

上述断言均做过反向验证：分别回退对应改动后，用例确实失败。

Schannel 由 fixture 模拟，不是 Windows 真机 CI。这是已知的测试边界——但本项目的立场是
**明确拒绝**原生 Schannel，而不是宣称支持原生 Windows，因此不需要真机来证明「能跑」。
